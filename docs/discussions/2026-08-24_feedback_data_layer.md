# 有本さんのフィードバックとデータ層リファクタリングの方針(Phase 19 の課題)

- 日付: 2026-08-24
- 相手: Claude (Fable 5)
- 位置づけ: **Phase 19 の方向を決めた記録**。Phase 18(ライブラリの整流化)の設計書
  `docs/plans/phase18_library_single_entry.md` と対になる。着手前にこの記録を読むこと

---

## 1. 経緯

先週分の進捗を有本さんに共有した際、開発者から「登録を増やす手段が無く、
サンプルの2件しか存在できない。ファイルを何個置いても既存2件のどちらかに
上書きするしかない」とコメントした。それに対する有本さんのフィードバック:

> 細かい実装みないとわかりませんが、データに対してシステムが柔軟になって
> なさそうなので、データをいくつでも増やしても大丈夫にして、データの変更も
> 全体的にきちんと反映されるように refactoring していく必要がありそうですね。
> サーバとブラウザ、完全にはリアルタイムにデータは同期できませんが、サーバ
> から参照されるデータを正として適当なタイミングで保存して reload しても
> 矛盾ないように詰めていくとよさそうです。
> かつ、このデータの読み書きをきれいな api 経由でできるようにしておくと、
> サービス化するときも比較的簡単にサーバに乗せてサービス化出来ます。

## 2. 前提の訂正(2026-08-24 の検証で判明)

「いくつでも増やせない」は実態と違った。Phase 15 以降、「Add track from
audio…」でトラックは何件でも追加できる。開発者がそれに気づけなかった原因は
モデルの硬さではなく**入口の混乱**(役割の違うプルダウンが2つ、隠れた
フィルタルール、ノードの重なり)で、これは Phase 18 の設計書に切り出した。

つまり有本さんの指摘のうち「柔軟に」の部分は入口の問題として Phase 18 で
解消し、残る本体が Phase 19 になる。

## 3. 指摘の分解と現状のギャップ

**(a) データの変更が全体にきちんと反映されること**
→ Phase 18 で「矛盾したデータを作れる入口を塞ぐ」形で対応(反映を鍛える
のではなく、反映が壊れる原因を消す)。

**(b) サーバのデータを正とし、適当なタイミングで保存、reload しても矛盾がない**
→ 未対応。現状のギャップ:
- 保存は手動の Save ボタンのみ。押し忘れるとサーバ(=正)と画面が乖離する
- 音源のファイル名・長さはブラウザの一時状態(`trackAudioInfo`)にだけ
  あり、プロジェクト JSON に保存されない。`Track.durationSec` は型に
  あるのに書かれていない

**(c) データの読み書きをきれいな API 経由にし、サービス化に備える**
→ 未対応。現状のギャップ:
- `/api/tracks` という名前で実際は音源ファイル一覧を返している(名前と
  実態のずれ)
- プロジェクトは全体を丸ごと GET/PUT する一本のみ

## 4. Phase 19 の方向(未設計。設計書はまだ無い)

1. **音源情報のプロジェクトへの永続化**: `Track.durationSec` をきちんと
   書き、reload で消える情報を無くす
2. **自動保存**: 変更後に少し置いて自動保存(手動 Save は残してよい)。
   「適当なタイミングで保存して reload しても矛盾ない」への回答
3. **API の整理**: `/api/audio-files`(音源ファイル一覧)と `/api/project`
   に分離・改名。トラック単位の CRUD API までは踏み込まない(サービス化の
   本格的な一歩は、必要になったときに別途決める)

**サーバのスコープについて**: CLAUDE.md は「サーバの役割は明示的な要望
なしに広げない」と定めている。上記 3 点は 2026-08-24 に開発者が有本さんの
フィードバックを受けて**明示的に要望した**リファクタリングであり、この記録が
その要望の記録を兼ねる。ただし内容は既存の2つの役割(音源ファイルの配信、
プロジェクト JSON の読み書き)の整理であって、新しい役割(認証・DB・
アップロード等)は引き続き追加しない。

## 5. 順番と理由

**Phase 18(整流化)→ Phase 19(データ層)** の2段構え。

- 矛盾したデータを作れる入口を残したまま同期を整えると、「同期はきれいに
  なったが、同期される中身が壊れている」ことになるため、入口を先に塞ぐ
- Phase 18 は UI の振る舞いの変更(要合意)、Phase 19 はデータ層の変更で、
  性質の違う作業。small steps の方針に沿って分ける
