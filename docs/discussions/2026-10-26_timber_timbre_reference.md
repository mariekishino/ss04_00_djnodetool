## 2. 作品の仕組みを 5 つの層で読む

資料から読み取れる構造を、音の処理の流れとして 5 層に分けた。
この分け方は Claude の整理であって、資料の章立てそのものではない。

| 層 | Timber Timbre での中身 |
|---|---|
| 音の経路 | 音源 → フィルター → VCA(電圧で動く音量)→ ミキサー → PA。このひとまとまりを「音の層」と呼び、23 層を重ねる。一部はエフェクトへ分岐して戻る |
| 制御信号 | コンピューターから出す制御電圧(CV)24 本。役割は音量 10、音色 7、エフェクト 3、音程 2 など。音の経路とは別の配線として引かれる |
| 状態と遷移 | 24 本の CV 値の組を「基準設定」として 12 組用意し、8 分かけて次の設定へ連続的に移る。巡る順序は周ごとに変わる |
| 観測と補正 | 出た音を Mac に戻して解析し、ルールで補正する。5 分ごとに Claude がスペクトログラムと測定値の要約を見て補正案を出し、案は検査を通ってから反映される |
| 可視化 | 同じ CV から映像を描き、信号の流れ図と Claude との対話を来場者に見せる |

### 学びとして押さえておきたい点

- **音声と制御は別の線。** モジュラーでは「音が通る線」と「音を動かす線」を
  区別して配線する。資料の接続内訳も音声 115 本、CV 158 本と分けて数えている。
  音量を変える、フィルターを開ける、といった操作はすべて「制御の線に値を
  流す」ことで実現する
- **音の層という単位。** 音源ひとつに、音色を整えるフィルターと音量を決める
  VCA を付け、ミキサーに送るまでがひとまとまり。23 層あるが、どの層も
  同じ形をしている
- **状態の組と、その間の移り変わり。** 「いま鳴っている音」は CV 24 本の
  値の組で決まる。別の組へ 8 分かけてなめらかに移ることで、音が変わる。
  断片を並べるのではなく、状態から状態への遷移として音楽を組み立てている
- **人が決め、計算で絞り、人が選ぶ。** モジュールの選択や配線は計算で候補を
  出しているが、目標を決めるのも最後に選ぶのも人。資料は「最適性を証明した
  範囲」と「人が手で差し替えた範囲」を分けて書いている
- **AI の案は検査を通る。** Claude の補正案は 1 回最大 4 本、1 回の変更幅と
  変化の速さに上限、音程(KEY)は対象外、ルール補正と逆向きの案は却下、
  という順で検査される。優先順位は「大きすぎ → 小さすぎ → Claude →
  ノイズ → 帯域の偏り → 単調さ」。AI は最終値を直接書き換えない
- **解析には要約だけを渡す。** 音声波形や特徴ベクトルそのものは Claude に
  送らず、スペクトログラム画像と数値の要約にして渡している
- **検証の範囲を正直に書く。** 「設計データ上の検査であって実機の測定では
  ない」「シミュレーションであって会場の実測ではない」という注記が各所に
  ある

## 3. NodeMix Canvas を同じ 5 層で見る

無理に合わせるためではなく、自分たちの構成がどの層の話なのかを見るための
対応表。

| 層 | NodeMix Canvas の現状 | 計画・未決との関係 |
|---|---|---|
| 音の経路 | 曲 → 音量(GainNode)→ 出力(`src/audio/audioEngine.ts`) | 2026-10-08 の議論 4.3「チャンネルストリップ」案(曲 → フィルター → EQ → エフェクト → 音量)は、作品の「音の層」とほぼ同じ形 |
| 制御信号 | `fadeDurationSec` による音量のランプだけ | Spotify の「曲線」(音量 10 種、EQ 8 種など)は、制御信号の時間変化に名前を付けたもの。CV と同じ役割 |
| 状態と遷移 | ノードとエッジそのもの。曲が状態、エッジが遷移 | Spotify のプリセットは「曲線の組に名前を付けたもの」で、作品の基準設定と同じ考え方 |
| 観測と補正 | 無し | 2026-07-10 に決めた Player / Analyzer 分離。Analyzer はまだ作らない |
| 可視化 | デッキパネルと波形(Phase 16、17) | 作品の信号の流れ図(入力 → 信号 → 駆動 → 出力)に相当するものは無い |

## 4. 設計に関係しうる示唆(採用は未定)

学びの副産物として、将来の設計で思い出せるよう書いておく。
どれもこの記録で決めるものではない。

1. **曲線を、動かす対象から独立した型にする。** 作品では CV は値の列で、
   それが音量に繋がるか音色に繋がるかは配線で決まる。第 1 段階(窓・位置・
   音量)の設計書を書くとき、曲線を音量専用にせず「曲線の種類 + 対象
   パラメータ」の形で持てば、第 3 段階(フィルター・EQ)で同じ型を使える。
   Web Audio では音量もカットオフも同じ AudioParam なので、再生側も一本化
   できる。今の `src/audio/audioEngine.ts` では、制御の側が `rampIn`、
   `rampInThenOut`、`fadeOutActiveVoices` の 3 関数に分かれ、cut / fade /
   crossfade の分岐が `playTransition` と `transitionToNode` に 2 回ある。
   曲線の型を入れるとき、置き換わるのはこの部分(2026-10-26 に確認。
   今は変えない)
2. **「提案 → 検査 → なめらかに反映」を AI 支援の決まりごとにする。** 将来
   「次の曲を提案する」機能を入れるとき、AI は project を直接書き換えず、
   `src/domain` の純粋なルール(`edgeRules`、`sanitizeFadeDuration` の延長)を
   通してから反映する
3. **Analyzer には要約だけを渡す。** Player / Analyzer 分離の境界ルール
   (`Float32Array` と数値だけ)と同じ発想で、方針が合っていることの確認
4. **遷移の順序を評価して選ぶ。** 作品は 12 設定を巡る順序を 400 通り比べて
   選んでいる。未解決課題「NEXT デッキ・分岐の選択」は、エッジに相性
   (BPM 差、Camelot キーの隣接)を持たせれば同じ形の話になる。今は実装
   しない
5. **設計書に「検証した範囲 / していない範囲」の節を置く。** 実装ログの
   「音が実際に鳴るかは手動確認に委ねる」と同じ姿勢を、計画段階にも持ち込む

## 5. そのまま持ち込まないもの

- 規模と最適化(124 台のモジュール選択を CP-SAT で解く)。学習として面白いが
  「小さな一歩」の方針と相反する
- 自律ループ、センサー、映像生成。作品の核だが、NodeMix の製品ビジョンは
  「ユーザーが音楽の地図を操作する」側にあり、AI は後から支援する立場
