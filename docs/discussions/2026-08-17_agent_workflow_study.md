## 0. なぜこれを検討するか

このプロジェクトのコードはほぼすべて AI が書いている。そのため「人が書く前提」で
組まれた開発プロセスのままでは、**生成量に検証が追いつかない**という問題が起きる。

実際、今週この形の失敗を2件起こしている(第3節)。一般論ではなく、**すでに経験した
失敗の再発防止**として検討する。

## 1. 参照資料

### 資料A: 開発ルールの提案(有本さんより共有)

要点:

- 関数はできるだけ**小さな純粋関数**に分割し、網羅的にテストする
- **Lint を厳しく**する。`any` や cast は禁止。SonarJS 等で長いファイル・長い関数・
  複雑な関数もエラーにする
- AI 時代は**テストを書くコストがほぼゼロ**。正常系だけでなく Edge / Corner / Error
  ケースまで作らせ、想定したエラーが実際に起きるかも確認する
- **Mutation Testing**: わざとソースを壊してテストが落ちるか確認し、テスト漏れを見つける
- AI は**重複コードを作りがち**なので、ツールで自動検出して減らす
- **CI を活用**する(lint / 型 / テスト / mutation / 重複)
- **異なる AI 同士で Cross Review** させ、連続して LGTM になるまで収束させる
- 時間がかかるなら **Agent を並列化**する(4〜8程度が扱いやすい)
- とにかく**小さく、シンプルに保つ**。人にも AI にも理解・テスト・レビューしやすく、
  Context Window も有効に使える

### 資料B: 論文(Discord のコミュニティで開発者が共有)

> "AI-Assisted Semiconductor Engineering for Edge-AI Hardware —
> A YOLO26-Oriented Feasibility Study with Expert Review and Implementation Feedback"
> Technical preprint, July 2026

半導体チップ設計を AI エージェントで行った実現可能性調査。約1ヶ月。要点:

- 専門家が**アーキテクチャ制約と受け入れ基準**を定め、エージェントが生成し、
  **実行可能な参照実装と EDA ツールの結果が、その成果物を次に進めてよいか決める**
- **証拠の階層**を定義している:
  存在する → 構造が正しい → 機能が正しい → 物理的に成立する → 出荷可能。
  **ある段階の結果を、必要な実験なしに次の段階へ昇格させない**
- 得られた成果と同じ熱量で「**何が証明できていないか**」を列挙している
  (フルコアの機能・物理クロージャ、GDS、シリコン、生産性向上の測定は未達)
- 教訓6つ: アーキテクチャは明示され続けること / **生成と受け入れは別の機能**である /
  機能の証拠はワークロードに沿うこと / 物理的な証拠は早く得ること /
  **出自(provenance)は正しさの一部**である / 作業範囲は制御されるべきこと

## 2. 2つの関係 — 共通点と、論文が付け加えているもの

**共通しているのは「生成ではなく受け入れの基準こそが本体」**という主張。
AI が書けること自体は前提で、価値を決めるのは**機械が判定できるゲート**の設計。

ただし論文は一段深い点を加えている。資料Aは主に「コード単体の品質」(lint・テスト・
重複・複雑度)を扱うが、論文の核心は**証拠の階層**であり、その最重要の失敗例は:

> 1枚の画像でキャリブレーションし、その同じ経路でテストしたら成功に見えた。
> しかし画像を増やしたら崩れた

**自分が用意した狭い検証環境で通ることと、本当に動くことは別**、という指摘。
lint とユニットテストはこの失敗を素通りさせる。だから論文は「独立した実行可能な
参照」と「広い入力セット」を要求している。加えて、資料Aには無い観点として
**出自(そのコードはどこから来たのか)**を正しさの一部として扱っている。

## 3. このプロジェクトで実際に起きた、対応する失敗

| 論文の失敗モード | このプロジェクトで起きたこと |
|---|---|
| 狭い検証で通ってしまう | `.gitignore` が `src/audio/` まで無視し、**lint・型チェック・テスト91件が全部通ったままリポジトリが壊れていた**。「別環境で clone してビルドする」という段階が検証に無かった |
| 出自の偽り(存在しない IP を抽出したと称する) | mock データが**実在しないファイル**を `audioUrl` に書いていた。もっともらしいが根拠が無い |

| raw regression archive が残っていない | ブラウザ検証スクリプトを毎回**一時ディレクトリに書いて捨てている**。「波形が 10→44→22→2」等の結果は週報にあるが、**再実行する手段がリポジトリに無い** |

## 4. 現状の棚卸し

できていること:

- 判断ロジックを**純粋関数として分離**し、単体テストしている
  (`edgeRules`, `transitionTiming`, `playbackSequence`, `trackRules`, `waveform`,
  `playbackProgress`, `formatTime` など)。テスト91件
- TypeScript、`any` を避ける方針は `CLAUDE.md` に明記済み
- フェーズごとに設計書 → 実装 → decision log を残し、決定の理由が追える

できていないこと:

- **CI が無い**(GitHub Actions 未設定)。今週の事故はここだけで防げた
- **クリーンな clone からのビルド検証**が工程に無い
- **ブラウザ検証がリポジトリに残らない**(第3節)
- Mutation Testing、重複検出、複雑度チェックが無い
- レビューが単一エージェント(私)のみ。**自分のバグは自分では見つけられなかった**
  (gitignore の件、キャッシュ無効化の呼び忘れの件)
- React コンポーネントとサーバーにテストが無い

## 5. マルチエージェントについての見立て

やる価値はある。ただし**順序を誤ると逆効果**になる。

エージェントを増やすと**生成量が増える**。判定する仕組みが無いまま生成量だけ増やすと、
レビュー負荷がすべて人間に来る。論文が繰り返し述べている「生成と受け入れは別の機能で
あり、レビュー工数はコストとして測るべき」がそのまま当てはまる。

また、**このプロジェクトの現在のボトルネックは生成速度ではない**。今週も時間を使ったのは
「何を作るべきか決める議論」であり、それは正しい使い方だった。マルチエージェントは
そこを速くしない。効くのは**検証と監査**の側。

したがって推奨順序:

1. **機械が判定するゲートを作る**(エージェント不要)
2. **クロスレビューを工程に入れる** ← マルチエージェントの本命。単なる高速化ではなく
   **盲点の補完**。別のエージェントに「新規ファイルが実際にコミットされているか」
   「キャッシュ無効化の漏れが無いか」といった観点で監査させる
3. **並列化は扇形に広がる作業に限る**(全コンポーネントの観点監査、複数の純粋関数への
   エッジケーステスト生成など)。機能開発の並列化は、この規模では競合と手戻りを生む

## 6. 次回の進め方(案)

| 順 | やること | 狙い | 規模 |
|---|---|---|---|
| 1 | CI 導入(lint / 型 / テスト / **クリーンcloneビルド**) | 今週の事故の再発防止 | 半日 |
| 2 | 検証スクリプトのリポジトリ化(`e2e/`)と CI 実行 | 捨てている検証を資産にする | 半日 |
| 3 | クロスレビュー工程の試行 | 指摘の質を評価してから常設を判断 | 1回試す |
| 4 | 厳格化(SonarJS で複雑度・重複、Mutation Testing) | 3の結果を見てから | 未定 |
| 5 | 並列エージェントの実験(監査系タスクで) | 効く範囲を見極める | 未定 |

結論が出た項目から `docs/11_development_workflow.md` に反映し、決定は decision log に
記録する。

## 7. 検討時の注意

- 資料Aの項目を**全部いきなり入れない**。このプロジェクトは1人・小規模であり、
  論文の事例(1ヶ月・複数ワークストリーム・専門家チーム)とは前提が違う。
  費用対効果の高い順に入れ、効果を確認してから次に進む
- クロスレビューは「**異なる**AI 同士」であることに意味がある。同じモデルの同じ癖では
  盲点が重なる可能性がある
- 論文が最も強調しているのは手法ではなく**態度**である。すなわち、
  **できたことと同じ精度で、できていないことを書く**こと。週報や decision log で
  すでに実践している方針と一致している
