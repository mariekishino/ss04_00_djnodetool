## 2. 今の仕組み(議論の前提)

トランジションは 3 層でできている。

| 層 | 場所 | 内容 |
|---|---|---|
| データ | `src/domain/types.ts` の `TransitionEdge` | from/to、種類(cut / fade / crossfade)、フェード秒。**位置を表す場所は無い** |
| タイミングの規則 | `src/audio/transitionTiming.ts` | 「曲 A の終わりのフェード秒前に繋ぎ始める」。入る側は常に曲 B の先頭 |
| 実行 | `src/audio/sequencePlayer.ts`、`src/audio/audioEngine.ts` | タイマーで繋ぎ時刻を待ち、音を切り替える。分岐は最初に作ったエッジを辿る |

## 3. Spotify の画面の読み解き

見た目は多機能だが、構造は一つに整理できる。

- **トランジション窓**が一つあり、上に曲 A、下に曲 B の波形が重なる
- 曲の位置は窓の中で動かすのではなく、**曲の波形のほうを左右にずらす**。
  これで「A のどこで抜けて、B のどこから入るか」が決まる
- 音量・イコライザ・フィルター・エフェクト・ルーピングの 5 項目は、
  それぞれ**窓の上に描かれた曲線の組(A の線と B の線)**。選択肢は
  曲線の名前にすぎない(音量 10 種、EQ 8 種、フィルター 11 種、
  エフェクト 12 種、ルーピング 6 種。一覧は開発者のメッセージに記録済み)
- プリセット(オート / フェード / ライズ / ブレンド / ウェーブ / メルト /
  スラム / ディゾルブ / サージ / アフターグロー / なし)は、5 項目の
  組み合わせに名前を付けたもの
- 曲一覧には **BPM、長さ、キー**が並ぶ。キーは Camelot 表記(8B = C major
  など。A が短調、B が長調)。DJ が次の曲を選ぶのに必要な 3 つの数字
- **再生速度の変更は曲ごと**に、トランジションとは別の画面にある

訂正: Claude は当初「8B / 5B」を小節数と推測したが、開発者が調べて
Camelot 表記のキーだと判明した。

## 4. 現在の設計への影響(5 点)

### 4.1 位置はエッジのもの

「位置はエッジの属性か、曲の属性か」が最上流の論点だったが、Spotify は
「この 2 曲のこの繋ぎ」ごとに設定しており、**エッジに持つ**と決めた。
データとしては「窓(長さ、A の位置、B の位置)+ 項目ごとの曲線名」。

今の cut / fade / crossfade は音量 10 種のうち 3 つに相当するので、
作り直しではなく一般化で済む。

### 4.2 時間の単位が「拍」になる

選択肢に「1 小節」「4 ビートループ」があり、窓の長さや位置を拍で持つには
各曲の **BPM と最初の拍の位置**が必要。BPM は手入力(`Track.bpm`)で、
拍の位置はまだ持っていない。これが Track に加わり、将来の Analyzer
(自動検出)の最初の仕事がここになる。

### 4.3 音の経路が「チャンネルストリップ」になる

今は 曲 → 音量 → 出力。フィルター・EQ・エフェクトを入れるには
曲 → フィルター → 3 バンド EQ → エフェクト → 音量 → 出力 を曲ごとに持つ
形になる。使わない段は素通し。Player は JS + Web Audio のまま、という
2026-07-10 の方針の範囲内。

### 4.4 保存形式が変わる

エッジの `transitionType` と `fadeDurationSec` は、音量の曲線名と窓の
長さから導ける値になる。古い JSON の読み替えが要る。Phase 19(データ層)
と時期が重なるので順番を考える。

### 4.5 再生速度は保存せず、繋ぐ瞬間に計算する(提案・確認待ち)

当初 Claude は「速度は曲に 1 つ持つ(Spotify と同じ)」を推奨したが、
開発者の「通常の DJ は繋ぐタイミングで速度を変えているのでは」という
指摘で訂正した。DJ の動作は:

1. 鳴っている曲 A の速度はそのまま
2. 次の曲 B のピッチフェーダーで、B の BPM を A の今の BPM に合わせる
3. 繋ぐ。以後は B がその速度で鳴り、次の曲 C は B の今の BPM に合わせる

つまり速度は固定の数字ではなく、**繋ぐ瞬間に前の曲との関係から決まる値**。
保存する必要が無い。

- 必要なデータは両方の `Track.bpm` だけ
- 繋ぐ瞬間に「B の速度 = 今鳴っている BPM ÷ B の BPM」を計算して設定。
  Web Audio の音源は再生速度を持ち、開始前の設定も再生中の変更もできる
- どちらかの BPM が未入力なら等速
- 「Play」(1 曲)は等速。「Play from here」で辿るときだけ 2 曲目以降が
  前の曲に合わせる
- テンポは連鎖で引き継がれる(A 120 → B 126 → C 130 なら B も C も 120)。
  途中で元の速度へ戻す操作は後から足せる。最初は「引き継ぐだけ」
- 音程は速度と一緒に変わる(レコードのピッチフェーダーと同じ)。音程を
  保つ伸縮は別ライブラリの話で、必要になったら考える
- 実装で触るのは、音源の速度設定と、速度で曲の長さが変わるので繋ぎの
  タイマーと進捗表示をそれに合わせること

## 5. 正直に書いておく制約

- **「オート」は解析の産物**なので作れない。プリセットは手で定義した
  固定の組み合わせになる
- 項目ごとの重さが違う。音量は今の延長、フィルターと EQ は Web Audio の
  標準部品、エフェクト(リバーブ、エコー)は部品が増える、ルーピングは
  拍の位置が無いと成立しない
- キー(Camelot)は `Track.key` にそのまま入る。「隣の数字、または同じ
  数字の A と B は相性が良い」と機械的に判定できるので、将来のエッジ提案
  (製品ビジョンの AI 支援トランジション)の足がかりになるが、今は入れない

## 6. 決まったこと / 提案中 / 未決

**決まったこと**

- Spotify の構造を参考にする
- 位置はエッジに持つ(4.1)
- 全部一度にやらない。最初の一歩は**窓・位置・音量**

**提案中(開発者の「いい」待ち)**

- 再生速度は保存せず繋ぐ瞬間に BPM から計算する(4.5)
- 段階の順序案: ① 窓・位置・音量 → ② 速度合わせ → ③ フィルター・EQ
  → ④ エフェクト → ⑤ ルーピング(拍位置が前提)
- Phase 19 との順番: この議論でエッジのデータ形を先に決めてから Phase 19
  を小さく済ませ、その後トランジションを段階的に実装

**未決(ここでは決めない)**

- 最初の拍の位置をどう入力するか(波形クリックで指定、が Phase 17 の
  延長で作れる)
- NEXT デッキのルール。「選択中のエッジの行き先」と自然に決まる方向が
  見えたが、未解決の課題の記録のとおり実装前に合意を取る
- ライブラリの分類(1 曲 / エフェクト素材)は引き続き未解決
