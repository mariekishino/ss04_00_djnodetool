# 未解決の課題: トラック名と音源のずれ / ライブラリの分類

- 日付: 2026-08-17
- 相手: Claude (Opus 5)
- 位置づけ: **未解決の課題の記録**。修正方針は意図的に未決定。着手前にこの記録を読むこと

---

## 1. 何が起きるか

Track Library には音源を紐づける入口が2つあり、片方が矛盾を生む。

**入口A: 各トラックのカード内プルダウン**(Phase 14)

既存トラックの**音源だけ**を差し替える。タイトル・アーティスト・BPM は元のまま残る。

再現手順:

1. `Night Drive`(mock、Sample Artist、110 BPM)のカード内プルダウンで `pianobase_01.mp3` を選ぶ
2. `Add to Canvas` を押す
3. キャンバスのノードに「Night Drive / Sample Artist」と表示される

鳴っているのは `pianobase_01.mp3` なのに、トラックの情報は別の曲のもの。ノード名で曲を判別できない。

| 項目 | 値 | 実態 |
|---|---|---|
| タイトル | Night Drive | 別の曲を指している |
| アーティスト | Sample Artist | 誤り |
| BPM | 110 | 誤り |
| audioUrl | pianobase_01.mp3 | これだけ正しい |

**入口B: ライブラリ上部の「Add track from audio…」**(Phase 15)

ファイルから新しいトラックを作る。タイトルはファイル名由来なので**ずれない**。アーティストと BPM は空(ファイル名からは分からないため)。

## 2. なぜこうなっているか

Phase 14 の時点ではトラックが mock の2件で固定だったため、「既存トラックに音源を紐づける」以外に音を出す手段がなかった。Phase 15 で「ファイルからトラックを作る」が入った結果、入口Aは役目を終えつつあり、かつ**矛盾を生む唯一の経路**として残っている。

「プルダウンが2つあって紛らわしい」という使用感の問題も、同じ原因から出ている。

## 3. 修正案(いずれも未採用)

| 案 | 内容 | 備考 |
|---|---|---|
| A. 入口Aを廃止 | 1トラック = 1ファイルに固定。差し替えたいときは削除して追加し直す | 矛盾が原理的に起きない。プルダウンも1つになる |
| B. 差し替え時に名前も追従 | 選び直すとタイトルとノード名もファイル名に変わる | 差し替えは残るが、アーティスト・BPM は古いまま残る |
| C. ノードにファイル名を併記 | ノードに実際の曲名を並べて区別できるようにする | 最小の変更。ライブラリ側の食い違いは残る |

## 4. なぜ今決めないか(2026-08-17 の判断)

**ライブラリが扱う素材の種類が、今後増える見込みがあるため。**

- 1曲まるごと使うもの
- DTM で作ったエフェクト音のような、短い素材

これらを同じ一覧に混ぜるのではなく、「エフェクト音を選ぶところ」のように**分けたほうが頭の整理に使いやすい**、という見立てがある。

もしライブラリに分類(カテゴリ/セクション)が入るなら、「トラックと音源をどう結びつけるか」の適切な形も変わりうる。先に上の A〜C のどれかを実装すると、分類を入れる段階で作り直しになる可能性がある。よって**分類の要否を先に決め、その後にこの課題を詰める**。

## 5. 次に詰めるときの論点

1. ライブラリに分類は必要か。必要なら、種類は `Track` の属性(例: `kind: "song" | "effect"`)か、別のエンティティか
2. エフェクト音は「1曲まるごと」と同じ再生・トランジションの扱いでよいか(短い素材にクロスフェード秒数は意味を持つか)
3. その結論を踏まえて、上の A〜C のどれを採るか
4. アーティスト・BPM をどこから得るか。ファイル名からは分からない。MP3 の ID3 タグを読む案があり、その場合はサーバー側で読むのが素直(BPM は将来 Analyzer が埋める領域)

## 6. 現時点の回避策

**入口Bだけを使う**。`/audio` に置いたファイルを「Add track from audio…」で追加すれば、名前と中身は一致する。

mock の3件(Night Drive / Blue Memory / Midnight Piano Drift)のカード内プルダウンで音源を差し替えると、上記のずれが起きる。
