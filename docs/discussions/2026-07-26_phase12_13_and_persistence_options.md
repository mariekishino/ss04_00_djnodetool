## 2. 週報へのフィードバックで出た指摘

> 現状ってブラウザ上で完結している感じですか? ファイルの保存程度であれば、サーバも簡単にできますし、メタデータも JSON でサーバ保存すれば DB などは不要なので、local で使う分にはその方向で簡単に作れると思います

**事実確認**: 指摘のとおり、現状は完全にブラウザ内で完結している。

- プロジェクト(メタデータ)= JSON ファイルのダウンロード/読み込み
- 音声ファイル = メモリ保持のみ。**リロードで消える**(Phase 11 で「メモリのみ」と割り切った結果)

バックエンドを持たないのは `CLAUDE.md` の方針(MVP はフロントエンドのみ)に基づく意図的な制約。

## 3. 永続化方式の選択肢(次フェーズで決める)

音声がリロードで消える問題への対処として、3案を比較対象とする。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A. IndexedDB | 音声データをブラウザ内DBに複製 | フロントのみで完結 | 実装が回りくどい。ブラウザ内DBの学習が主題に割り込む。容量を食う |
| B. File System Access API | ローカルファイルへの参照許可を記憶 | コピー不要 | 対応が実質 Chrome 系のみ |
| **C. ローカルサーバー**(今回追加) | 音声を配信し、プロジェクト JSON を読み書きする最小のサーバー | URL で普通に参照でき、リロードしても生きる。実装も理解も単純。DB 不要 | プロセスが2つになる。CORS/プロキシ設定。ファイル置き場の規約決めが必要 |

**現時点の見立て**: C が有力。ドメイン型に既に存在しながら未使用の `Track.audioUrl` が、本来の意味で使えるようになる点も大きい。

**導入する場合の線引き**(方針「バックエンドを増やさない」との両立):

- 静的な音声配信 + プロジェクト JSON の読み書きのみ
- 認証・DB・アップロード UI・クラウド同期には踏み込まない
